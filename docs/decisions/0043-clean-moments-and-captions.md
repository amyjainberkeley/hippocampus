# ADR-0043: Moments are read without their window's chrome, and each says what it was about

- Status: Accepted (2026-10-18)
- Extends: the reader in `core/brain/src/reading.rs`, ADR-0016 (the store), ADR-0039 (the brief model boundary)

## Context

History showed each moment as one raw line of what the reader stored. For memories saved before 0.3, read before windows were classified, that line was often a browser's tab strip: tab titles cut short and joined by close buttons, with favicons read as letters. Nothing said what the moment was about. The 0.3 reader sets a window's tabs, sidebars and bars apart for new reads, but older memories kept the old reader's text, and AI tools saw the same tab strips through `mci_recall` and `mci_context`.

## Decision

1. **Chrome is set apart, never deleted, and only from older text, at a window's edges.** The reader moves a line that is window chrome out of what was being read (`main`) into the rest of the window (`rest`, "Also in this window"). A window the capture helper classified keeps its content whole: the helper knew where each line sat on the screen. In older text, only the run of lines at the top and the run at the bottom are looked at, each ending at the first line that is not chrome; in the middle only what can be nothing else moves (an editor's status bar and row of panel names, Slack's sidebar headings of two words or more). So a reply "More", a heading "## TIMELINE", steps "System Settings > Privacy > Accessibility" and a formula with "×" stay. By its own shape, place and window (`core/brain/src/chrome.rs`): a browser's tab strip (close buttons as ×, x, X or ⊗ but never after a number alone; the favicons of pinned tabs; three favicon-led tabs; the window's own title among other titles; Safari's wide gaps; a strip read over two lines), address bar, bookmarks bar and toolbar remnants in the window's first six lines, and there too a web app's row of menus, a search page's tabs, a site's menu ending in its "Subscribe" or "Sign in" button, a lone "Share" or "Sign in", and a title bar with its star; the side navigation of Gmail, Google Calendar, GitHub, YouTube, LinkedIn, Notes, Finder and System Settings; an editor's tabs, side bar headings, breadcrumbs, panel names and status bar; Slack's top bar, sidebar headings and message box; Messages' one receipt and its message box. A terminal's text is kept as read but for a coding assistant's status line and empty input box at its bottom. The window's title and address come from the stored header. If moving a line would put a secret pattern together where kept pieces meet, nothing moves. Older text of a page or a document also reads in paragraphs.
2. **Chrome is learned from many frames, carefully.** A line of two words or more that windows of one app showed at their edges (their first eight or last four lines), outside code, tables and shell sessions, unchanged, in at least half of that app's frames of a day and under at least three different titles, is chrome: Safari's tab bar, Arc's sidebar, a site's menu. A chat app learns only its channel names. Only older text is learned from. A learned line counts only in the runs at the top and bottom, and not below the window's own name; a line a sidebar was read into loses only that start, outside code.
3. **The stored text never changes.** `events.text` keeps every byte and stays what search indexes, so a tab title still finds its moment. A moment's cleaned text and caption live in `moment_readings` (migration 0015), one row per moment, which cascades from its event and is deleted explicitly in every deletion transaction: forget one, delete a range, retention, wipe. The cleaned text is stored only when the learned rule changed it; otherwise the live reading is the same and nothing is stored twice.
4. **Each moment has a caption.** One short plain line ("Looking up how to type accents"). The on-device model writes it through `hippocampus-mind` (Apple Intelligence, or the person's model server on this Mac); without one, it is made from the window title, the app's kind of work and the page address with a few plain verbs, the app named from one table (`apps::name`, which the window reads too). A model's line is kept only when every word that says what the moment was about comes from that moment's own title, address, app name or text, and it names something the title does not; it says nothing about the person (no pronouns or feelings, and no word or phrase of a sensitive area, `core/brain/src/sensitive.rs`: work life, health, money, relationships, beliefs, identity or the law, the list the agent's inferred lines use); it speaks of a call only in a call's own window; and it passes the secret check stored text passes. The model is not asked about a moment whose title, address or text touches a sensitive area, nor about a window beside the one in use, which is named where it was open ("#launch, open in Slack") rather than given an activity. Captions are stored, not made on every scroll.
5. **Old memories are re-cleaned in the background.** The agent's re-clean worker reads the newest moments of past days without a row of the current rules version (`READING_VERSION`, 2 since the chrome and caption rules above), learns each app's chrome from that app's moments of the same local day, sampled across the day, and writes their rows; then it offers captions made from titles to the model, one request per window, each given only the batch's time left. A row is written only while the event with its id is still the moment that was read (time, app, title and text), so an id a deletion freed and a new capture took never receives it. It runs only on a power cable, out of Low Power Mode, and when nobody has touched the Mac for two minutes, read again before each request to the model; a batch stops after 20 seconds and the worker rests four times as long. A row of the current version is never made again, and a moment offered to the model is never offered again.
6. **AI tools get the cleaned text.** `mci_recall`, the listings and `mci_context` show the stored cleaned reading when there is one, else the live reading. Search still runs on the stored text.
7. **The unused brief model goes.** A standard build loads no Qwen3 model (ADR-0039). On launch it removes, once, the `Models/qwen3-1.7b-fp16` directory an earlier version downloaded, and nothing else; a build that bundles the model keeps it.

## Consequences

- Text the old reader ran together across columns (a sidebar and a message on one line) is only partly separated: a learned start comes off, the rest stays. Reading a kept screenshot again with the 0.3 reader would separate it fully; that is not done in the background (Read Again stays a choice the person makes).
- The worker's bound is on time, as the reader's is (ADR-0041): busy at most a fifth of the time it may run, and only then. The model's own work happens in its process.
- Raising `READING_VERSION` makes every row again, newest first, the next times the Mac is plugged in and idle. A day still being lived waits until it is over, so its moments are cleaned against the whole day; until then the live reading and a caption made from the title show.
- Lines in the middle of what was read that look like chrome stay there: some interleaved sidebar text in older memories stays too, which costs a little cleaning and never a line of what was read. A lone word ("Today") is never learned.
- The worker cannot lower its thread's priority class (the agent forbids `unsafe`); it bounds its work by time and conditions instead.
