# ADR-0044: A moment's text reads as typed blocks, and more wrapped lines join

- Status: Accepted (2026-10-19)
- Supplements: ADR-0043 (clean moments and captions)
- Ratifier: Amy ("yes do it make it clean, the context transcription should all make sense and make it formatted")

## Context

After ADR-0043, History showed a moment's text cleaned but as one block: a heading, a list and a code sample inside one article read as the same grey run of lines, drawn either all monospaced or all proportional. Joining still missed common wraps: a line that ends on "and" or "the" before a short line, a wrap just before a name, and answers in AI chats, which were kept line by line because their apps sat on the chat list.

## Decision

1. **Blocks only split `main`.** `core/brain/src/reading_blocks.rs` turns a reading's `main` into an ordered list of typed blocks: label, heading (level 1 at most once, or 2), byline, paragraph, list (markers as read, checkboxes known), code, terminal (byte for byte, prompt lines marked), table (only when cells are known, read with tabs), lines (short lines that stay apart), turn (a chat's speaker and time as read, then what was said), quote and meta. Every block holds only text of `main`, as read; a block's kind changes only how it is drawn. Blocks never put two pieces side by side that the reading kept apart. They are made when a reading is shown, from the stored or the live `main`, so a change to these rules needs no re-clean. The FFI's reading carries them as an additive `blocks` field; an AI tool gets `markdown()` of them and Copy Text copies `plain_text()`.
2. **Rules by kind of window.** Pages, documents, notes, PDFs and AI chats follow one set of document rules (the level-1 heading is the line that names the window; a byline is a date or "min read" near it; a section heading stands alone, follows a label, or comes before a long line, a list, code or a table, never inside a group of rows; two or more code lines in a row are code). Mail adds its subject, header lines, quotes and signature. A chat with people is turns when speaker lines are read, otherwise a paragraph per line: nothing is attributed to anyone, and alignment, colour or "you" are never guessed. A terminal is one block as read; a code editor's code is one block with its blank lines; a sheet is rows. No speaker is ever inferred in an AI chat.
3. **More wrapped lines join, each through the guard.** Besides the existing rule (J1), a line joins the next when it ends on a joining word (J2, not in a group of short lines and never before a list item, a speaker line or a heading), and, in a block of prose whose wrap edge two lines reach, when it fills the line and ends in a letter before a capital (J3) or ends a sentence (J4). AI chats read as prose. A chat with people joins only a line that fills the line, so two messages never merge. Two CJK characters join with no space; a line of one script never joins a line of another; code never joins. A join that would make one of the capture helper's secret patterns appear keeps only those two lines apart.
4. **Code's brackets and a signature's "--" stay.** N3 no longer drops a line of code's brackets ("}", "});") or "--": formatted text needs them.
5. **One text view.** The window draws the blocks in one read-only TextKit 2 text view, built off the main thread from design tokens only; a selection runs across paragraphs and copies plain text as it was read; VoiceOver has rotors for its headings, code and lists. Code, terminal output and table rows draw their box and hairlines through a layout fragment of their own.
6. **`READING_VERSION` is 3,** so stored readings are made again, newest first, by the re-clean job (ADR-0043). The caption rules did not change (`CAPTION_RULES_SINCE` is 2), so a line the on-device model wrote for a version 2 reading is kept while it is still grounded in the moment as it now reads, and a moment the model was already asked about is not asked again.

## Consequences

- A table read off the screen joins its cells with spaces (the capture helper's rule B1), so most screen-read tables are `lines` this release; text from the browser extension keeps its tabs and becomes a real table. Next: the helper writes a tab between a recognised table row's cells.
- J4 cannot tell a paragraph's last line that happens to reach the wrap edge from a wrapped one; such two sentences read as one paragraph, which reads well and loses no word.
- An older chat window read with its sidebar beside the messages still mixes the two in places; blocks show what was read and never guess who said what.
- A reading has at most 2,000 blocks, items, rows, cells, lines and marked prompts; past that the rest of `main` is one paragraph as read, so the window's bound on the reading's JSON always holds.
- Tests: `core/brain/tests/reading_blocks.rs` (golden blocks, Markdown and plain text for every kind of window, old and new; counterexamples; properties: nothing invented or lost, code byte for byte, deterministic, the secret corpus, the JSON bound, a budget of about 2 ms for a long page), `core/brain/tests/reading.rs` (J2 to J4, the guard), `core/brain/tests/chrome.rs`, `core/brain/tests/reclean.rs` (a model's caption outlasts the version), `mci-brain-ffi/tests/event_reading_blocks.rs`; in the window, `ReadingBlocksDecodingTests` (every golden decodes and copies as the brain copies it) and `FormattedReadingSnapshotTests`.
